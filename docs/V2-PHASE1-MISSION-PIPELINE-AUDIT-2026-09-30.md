# V2 Phase 1 Mission-Pipeline Audit — 2026-09-30

## Scope

This audit covers the Gazebo `edge-vision` interactive test session from
02:40 AM onward, recorded in episode
`20260930T024405_8d41e216673d`. It evaluates whether failures came from the
base language model or from the mission-planning architecture.

The tested language model was
`Qwen3-4B-Instruct-2507-Q4_K_M`, running locally through `llama.cpp` with a
4096-token context, temperature 0, and the plan-once visual-scheduling prompt.

## Executive conclusion

The dominant problem is the pipeline structure, with model capability as a
secondary contributor.

The LLM frequently expressed the operator's intent correctly in
`understood_intent`, but the mission still failed because the planner was also
required to manufacture exact flight coordinates, choose perception tools,
calculate derived values, write provenance strings, and satisfy strict
substring-style grounding rules in a single response. The validator then
rejected safe and obvious transformations such as “whole area” to a reviewed
360-degree scan, using the takeoff altitude for the following orbit, or
resolving “home” to the takeoff origin.

The 4B quantized model also made genuine mistakes: it converted “south 5 m” to
an incorrect east/west coordinate, selected YOLO for a building even though
the prompt explicitly says buildings require VLM inspection, and once proposed
`person` as a placeholder for a building. A stronger model would reduce these
mistakes, but it would not repair the structural rejection, missing motion
primitives, clarification loop, perception contract bug, or lack of bounded
conditional execution.

## Why the current structure prevents general-purpose behavior

### 1. One LLM call is doing too many different jobs

The planner must simultaneously perform natural-language understanding,
mission decomposition, tool routing, coordinate conversion, numerical
calculation, default selection, provenance generation, schema compliance, and
safety classification. These tasks have different failure modes. A small local
model can understand the intent and still fail the synthetic compiler protocol.

### 2. Provenance is being generated by the model instead of the system

The LLM must emit strings such as `operator`, `reviewed_policy:<key>`, and
`derived:<expression>`. The validator checks these strings and often rejects
the entire mission even when the intended behavior is safe. Provenance should
be attached by trusted code when it resolves operator values, policy defaults,
live state, and mathematical derivations—not authored as prose by the LLM.

### 3. The validator is reinterpreting language

Rules such as “the number must be numerically grounded in the source” make the
validator behave like a second, brittle NLP system. It rejects semantic
equivalences such as:

- “look around the whole area” -> bounded 360-degree scan from reviewed policy;
- “home” / “where you took off” -> autopilot home or local origin;
- “same as takeoff” -> the already grounded takeoff altitude;
- “south 5 metres” -> a relative NED displacement resolved from live pose.

The deterministic validator should validate final bounds, capabilities,
reference availability, and safety. It should not decide what the sentence
means.

### 4. The motion vocabulary is incomplete

There is no first-class relative movement objective. Natural requests such as
“move south 5 metres” are forced into an absolute `goto`, encouraging the model
to invent or miscalculate coordinates. There is also no safe bounded
`scan-until-condition-or-limit` objective, even though that is a core visual
drone behavior.

### 5. Visual tool routing is too dependent on LLM obedience

The system already knows that `person` is a YOLO class and `building` is not.
It also knows that buildings and damage require qualitative VLM inspection.
This capability mapping should be resolved from a registry after the LLM has
expressed the semantic visual query. The LLM should not be able to map a
building to `person` as a placeholder.

### 6. Clarification is accumulated as raw prose instead of filled into slots

Answers are appended as repeated `Operator clarification:` strings and the
entire prompt is replanned. There is no durable typed mission state saying, for
example, `orbit.center = home/local-origin` and `orbit.altitude = 8 m`. This is
why the system asks the same question repeatedly or moves on to another value
that was already obvious.

### 7. Planning is static where visual missions need bounded feedback

The plan-once executor expands a scan into a fixed list before flight. “Rotate
until you detect a building” needs a safe bounded feedback primitive:

1. rotate by a reviewed step;
2. call the selected visual tool;
3. stop early when the condition is met;
4. otherwise continue until a declared maximum angle or viewpoint count;
5. report not found when the bound is exhausted.

This gives the LLM semantic control without giving it direct motor authority.

### 8. An independent execution bug aborts otherwise valid plans

When a fresh LiDAR map has age exactly `0 ms`, the proto3 scalar is omitted by
`MessageToDict`. The freshness validator reads the omission as a missing age
and aborts. This caused both executable missions in the test window to RTL.

## Recommended architecture

Use four clearly separated stages:

```text
Natural operator prompt
    -> LLM semantic objective plan
    -> deterministic resolver/compiler
    -> small safety/capability validator
    -> bounded feedback executor and Drone API
```

### LLM semantic objective plan

The LLM should describe intent using semantic references, not manufacture
final coordinates or provenance text. Examples:

- `relative_move(direction=south, distance=5m)`
- `orbit(center=home, radius=5m, altitude=same_as_takeoff)`
- `bounded_visual_scan(query=building, stop_when=found, max_angle=360deg)`
- `visual_scan(queries=[people, suspicious_damage])`

It should decide whether a request is ready, genuinely ambiguous, or
unsupported, but it should ask only about choices that materially change the
mission.

### Deterministic resolver/compiler

Trusted code should:

- resolve `home` from autopilot/live state;
- resolve relative movement against the current local frame;
- carry the takeoff altitude into `same_as_takeoff`;
- apply reviewed limits and defaults;
- route exact detector classes to YOLO and qualitative queries to the VLM;
- combine compatible YOLO and VLM observations at the same scan viewpoints;
- attach value provenance automatically;
- compile semantic objectives into bounded Drone API actions.

This code assists the LLM; it does not invent the mission or drive objective
selection.

### Safety/capability validator

The validator should check only matters such as:

- action and sensor capability exists;
- all semantic references were resolved;
- coordinates, altitude, speed, yaw, radius, and duration are within limits;
- lifecycle and vehicle-state prerequisites are satisfied;
- obstacle/state evidence is fresh;
- conditional loops have hard bounds;
- the plan contains a safe termination or recovery path.

It should not require literal numeric substrings or LLM-written provenance.

### Bounded feedback executor

The executor should support bounded visual conditions while retaining hard
guardrails. The LLM selects the objective and observation policy before flight;
the executor performs the repeated yaw/move, observe, evaluate, and stop cycle.
Motor commands continue to pass through the Drone API, guardrails, safety
supervisor, and ArduPilot.

## Model recommendation

Do not treat a larger model as the first fix. First simplify the protocol,
add missing semantic primitives, make clarification stateful, and fix the
map-age contract. Then benchmark the current Qwen 4B Q4 model against a larger
8B/14B-class model on the same held-out prompt set.

The current model is likely adequate for many straightforward objectives after
the compiler burden is removed, but its direction conversion and visual-tool
mistakes show that it should not be trusted to calculate final flight geometry
or route unsupported visual classes without deterministic resolution.

## Decision

Phase 1 should not be declared general-purpose or ready for Phase 2 yet. The
next work should be a focused mission-pipeline correction, not more prompt
patches:

1. fix zero-age perception serialization/presence;
2. replace model-authored provenance with system-authored provenance;
3. introduce relative movement, semantic home references, and bounded
   conditional visual scans;
4. add deterministic YOLO/VLM capability routing and combined visual scans;
5. replace appended clarification prose with typed slot filling;
6. reduce the validator to capability, bounds, state, freshness, and safety;
7. rerun a held-out natural-language suite before considering a model upgrade.
