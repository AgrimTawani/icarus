# Audit: did the `feat/laya-decision-speed` branch nerf or clog the system? (2026-11-06)

Short answer: no clogging, a large speed gain, and two regressions the branch introduced. One is fixed here
(offline-verified, not yet flown); the other is small and still open. Laya itself is not in the system at all:
it was evaluated and rejected, so nothing of it runs at mission time.

Everything below is measured from `logs/episodes/` or from model-only replays (no simulator). The laptop was on
battery for this whole pass (59 % -> 19 %), so **no timing here was re-measured on AC and no sim was flown**;
token counts, memory and tool choices do not depend on power.

## Prompt size ("clogged with information?")

| | Before (2026-10-24) | Now |
|---|---|---|
| Prompt at the first decision | 7,994 tokens | 8,399 tokens (+5 %) |
| Tool catalogue | 26.8-28.2k chars, changed during the mission | 28.5k chars, fixed |
| Tokens the model actually reads per decision | all ~8-9.6k (cache missed) | median 145 new tokens |

The +5 % is the `registered_target` destination variant and the takeoff climb-rate field, now always present so
the catalogue never changes. Per-step additions (tool result + vehicle state) are 80-240 tokens.

## Where mission time goes now (13 AC-powered episodes, 2026-11-06 02:00-03:30)

- Wall time 3,423 s: model decisions 223 s (**7 %**), camera questions ~704 s (21 %, mostly concurrent with
  survey flight), the rest is flying.
- Inside a decision (median 2.2 s): generating the tool call 1.8 s (70 % of all decision time), prefill 0.26 s.
- Of all generated tokens, 14 % is free text before the call (44 of 170 decisions) and ~13 % is optional
  parameters restated at their default (`search_for_object` writes five of them every time).

So further decision-speed work can move mission time by a few percent at most.

## Regression 1 (fixed): camera questions shared the mission's server slot

With one slot, llama-server copied the displaced prompt into its RAM cache on every switch between the mission
conversation and an image.

- Measured offline: +~110 MiB of RAM per camera question (1.9 -> 4.2 GiB after 15 questions).
- A survey asks 53-88 questions; the cache then evicted the mission conversation. All 3 decisions after such
  surveys re-read the whole prompt: 10.1-11.1 s instead of ~2 s.
- 7 GiB of swap was in use on the test laptop afterwards.

Fix (`python/dcm/llama_runtime.py`): the mission conversation and camera questions each pin their own slot
(`--parallel 2 --kv-unified --cache-ram 0`, `id_slot` 0 / 1), and the mission context budget leaves room for the
camera slot. Offline result with the same test: RAM flat at ~1.9-2.4 GiB, mission cache intact after 15
questions (`cached=8915`). Unit tests cover the flags, slot ids and budget. **Not yet flown in a sim.**

## Regression 2 (open, small): an extra step before orbiting

After `search_for_object` found the object, the next call was:

| | orbit directly | approach_target | localize_target |
|---|---|---|---|
| 2026-10-24 (15 cases) | 9 | 4 | 1 |
| 2026-11-06 (16 cases) | 1 | 6 | 7 |

`localize_target` before `orbit` is never needed (orbit measures the object itself). It costs one decision plus a
localization, about 2-5 s per orbit mission; missions still completed. The likely cause is the always-visible
`registered_target` variant, but the choice at this point is a near-tie: replaying those 15 decisions on the
two-slot server picked `approach_target` 13 times and `localize_target` 0 times with no text change at all, and
three description rewordings moved it in both directions. None is shipped: no variant was reliably better.

## Not measured (needs AC power)

- Vision accuracy of the resident model at the 256-token CPU cap on the 24-frame benchmark (only 10 clear Gazebo
  frames were checked at that setting).
- A full replay of old decisions under the live catalogue (the one run here built the catalogue without vehicle
  defaults, so its 120/147 agreement is not a valid number).
- Any flight with the two-slot runtime.

## Research: other UAV agent projects

Full survey: [UAV-AGENT-ARCHITECTURES.md](UAV-AGENT-ARCHITECTURES.md). Its conclusions match the measurements
above: no surveyed project gets good results from a zero-shot 3-4B model as a multi-step UAV agent without
fine-tuning, and Icarus already has what the stronger designs converge on (composite skills, static catalogue,
executor guardrails, receipt check).

| Idea (source) | Verdict here |
|---|---|
| Executor-owned defaults: the model writes only what the operator said (TypeFly, Octopus v2) | Worth doing next: ~13 % of output tokens, ~1.6 s on each search call. Needs a replay on AC to confirm operator-given values still pass. |
| Start executing while the next call is generated (TypeFly) | ~4-6 s less hover per mission (~2 %), 150-250 lines, runs steps without seeing the previous result. Not worth the risk. |
| Failure results that list permitted recoveries (SPINE, BTGenBot-2) | Robustness, not speed; fits the open "what to do after a failed step" issues. Candidate. |
| Compact call syntax / DSL (MiniSpec) | 40-55 % fewer output tokens but leaves the model's trained tool format; no zero-shot small model shown doing it. No. |
| Tool retrieval, functional tokens, plan caching, single-shot plans | Save prompt tokens or network round trips we no longer pay; tool retrieval would break the cache. No. |
| LoRA fine-tune on own traces (SPINE, TinyAgent, DroneCATS) | The only lever shown to close the small-model gap; large, and tied to the catalogue. Later. |
